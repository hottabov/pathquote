# ТЗ: Unfinalize менеджером, ревізії квот, розділення підписів, лист клієнту

Репозиторій: PF Invoice / PathQuote.
Мова коду і назв полів — англійська, коментарі можна українською.

## 0. Контекст і мотивація

Живий тест на сейлсі показав: менеджер фіналізує квоту, потім бачить, що забув опцію до машини. Клієнту ще нічого не надіслано, але виправити вже не можна — unfinalize доступний тільки адміну. Це блокер.

Продажі тут — не покупка телефона. Обладнання дороге, менеджер і клієнт ганяють квоту туди-сюди тижнями, поки не дійдуть згоди. Менеджери вже зараз вручну дописують до номера `R1`, `R2`, `R3` і плодять копії квот. Треба зробити редагування легким і при цьому не втратити історію: у клієнта на руках PDF версії R1, і через місяць має бути видно, що саме він тоді отримав.

Три блоки робіт:
1. Unfinalize для менеджера + ревізії зі снапшотами.
2. Розділення підпису менеджера і підпису клієнта + адмінський `voidSignature`.
3. Діалог надсилання клієнту з передзаповненим листом і красивим HTML-шаблоном.

## 1. Модель статусів

```
DRAFT → FINALIZED → SENT → CLIENT_SIGNED → ACCEPTED
```

| Статус | Значення |
|---|---|
| `DRAFT` | редагується вільно |
| `FINALIZED` | зафіксовано, снапшот ревізії створено, клієнту ще не надіслано |
| `SENT` | лист із PDF пішов клієнту |
| `CLIENT_SIGNED` | клієнт підписав форму |
| `ACCEPTED` | прийнято в роботу, тут вимагається підпис менеджера |

`CANCELLED` — окремий термінальний статус, якщо він уже є в схемі, лишаємо як є.

Дозволені переходи:

| З | В | Хто | Умова |
|---|---|---|---|
| `DRAFT` | `FINALIZED` | owner, admin | валідація квоти проходить |
| `FINALIZED` | `DRAFT` | owner, admin | `clientSignedAt == null` |
| `FINALIZED` | `SENT` | owner, admin | — |
| `SENT` | `DRAFT` | owner, admin | `clientSignedAt == null` |
| `SENT` | `CLIENT_SIGNED` | клієнт за підписною лінкою | — |
| `CLIENT_SIGNED` | `DRAFT` | **тільки admin**, через `voidSignature` | обов'язкова причина |
| `CLIENT_SIGNED` | `ACCEPTED` | owner, admin | вимагається `managerSignedAt` |

Підпис менеджера більше **не** є умовою для `SENT`.

## 2. Зміни в схемі даних

Міграції називати за наявною конвенцією репозиторію (`z4*`).

```prisma
enum QuoteStatus { DRAFT FINALIZED SENT CLIENT_SIGNED ACCEPTED }

model Quote {
  // ...наявні поля
  status             QuoteStatus @default(DRAFT)
  revision           Int?        // null = ще жодного разу не фіналізована
  finalizedAt        DateTime?
  finalizedById      String?
  sentAt             DateTime?
  hasUnsentChanges   Boolean     @default(false)

  managerSignedAt    DateTime?
  managerSignedById  String?

  clientSignedAt     DateTime?
  clientSignedName   String?
  clientSignedEmail  String?
  clientSignedIp     String?
  signedRevisionId   String?     // яку саме ревізію підписав клієнт

  revisions          QuoteRevision[]
  emails             QuoteEmail[]
  events             QuoteEvent[]
}

model QuoteRevision {
  id           String   @id @default(cuid())
  quoteId      String
  revision     Int      // 0, 1, 2...
  label        String   // "PQ-2026-0123" або "PQ-2026-0123-R1"
  snapshot     Json     // повний зліпок квоти на момент фіналізації
  snapshotHash String   // sha256 від нормалізованого snapshot
  pdfPath      String?  // шлях до згенерованого PDF цієї ревізії
  total        Decimal
  createdAt    DateTime @default(now())
  createdById  String

  @@unique([quoteId, revision])
}

model QuoteEvent {
  id        String   @id @default(cuid())
  quoteId   String
  type      String   // FINALIZED | UNFINALIZED | SENT | CLIENT_SIGNED | MANAGER_SIGNED | SIGNATURE_VOIDED
  actorId   String?
  reason    String?
  meta      Json?
  createdAt DateTime @default(now())
}

model QuoteEmail {
  id           String   @id @default(cuid())
  quoteId      String
  revisionId   String
  to           String[]
  cc           String[]
  subject      String
  bodyText     String   // те, що менеджер реально відправив, після підстановки змінних
  sentAt       DateTime @default(now())
  sentById     String
  providerId   String?  // message id від поштового провайдера
}
```

Міграція наявних даних: для квот, що вже фіналізовані, виставити `revision = 0` і створити для них `QuoteRevision` зі снапшотом поточного стану, щоб історія не починалася з порожнечі.

## 3. Права доступу

| Дія | Manager (owner) | Manager (чужа квота) | Admin |
|---|---|---|---|
| Finalize | так | ні | так |
| Unfinalize (до підпису клієнта) | так | ні | так |
| Unfinalize (після підпису) | ні | ні | ні |
| `voidSignature` | ні | ні | так |
| Send to client | так | ні | так |

«Owner» — це creator квоти (або поле, яке в репозиторії вже виконує цю роль). Перевірку робити на сервері в кожному роуті, не тільки ховати кнопку в UI.

## 4. Unfinalize

`POST /api/quotes/[id]/unfinalize` (у стилі наявних роутів).

Логіка:
1. Перевірити права (owner або admin) і `clientSignedAt == null`. Інакше 403.
2. `status = DRAFT`.
3. Якщо попередній статус був `SENT` — виставити `hasUnsentChanges = true`.
4. Записати `QuoteEvent{ type: "UNFINALIZED", actorId, reason }`. Поле `reason` необов'язкове: якщо зробити його обов'язковим, менеджери писатимуть «.» і сенсу в ньому не буде.
5. Ревізії при unfinalize **не** створюються і не видаляються. Лічильник рухається тільки на finalize.

UI:
- Кнопка `Unfinalize` на сторінці квоти поруч із `Send`, видима власнику при `FINALIZED` / `SENT` і `clientSignedAt == null`.
- Підтвердження в діалозі. Якщо квота вже `SENT`, текст діалогу прямо каже: «Клієнт уже отримав версію {label}. Після змін потрібно буде надіслати квоту повторно».
- При `hasUnsentChanges = true` на сторінці квоти постійний банер: «Є зміни, не надіслані клієнту. Остання надіслана версія — {label} від {date}».
- При `CLIENT_SIGNED` кнопки немає взагалі (не disabled, а відсутня), замість неї для адміна — `Void signature`.

## 5. Ревізії

Нумерація:
- Перша фіналізація: `revision = 0`, label = номер квоти без суфікса, напр. `PQ-2026-0123`.
- Кожна наступна фіналізація: `revision = lastRevision + 1`, label = `PQ-2026-0123-R1`, далі `-R2`, `-R3`.

Захист від порожніх ревізій: на finalize порахувати `snapshotHash`. Якщо він збігається з хешем останньої ревізії (менеджер зробив unfinalize і нічого не змінив), нову ревізію **не** створювати і номер не збільшувати — просто повернути статус у `FINALIZED`. Інакше номери бігтимуть від кожного випадкового кліку.

Що робить finalize:
1. Валідація квоти (наявна логіка).
2. Зібрати повний снапшот: позиції, опції, кількості, ціни, знижки, валюта, умови, реквізити клієнта, дані менеджера, все, з чого рендериться аркуш. Снапшот має бути самодостатнім: рендер ревізії не повинен залежати від поточного стану каталогу.
3. Порахувати `snapshotHash` від нормалізованого JSON (стабільний порядок ключів).
4. Створити `QuoteRevision` (якщо хеш новий), згенерувати PDF через наявний Gotenberg-пайплайн і зберегти шлях у `pdfPath`.
5. `status = FINALIZED`, `finalizedAt`, `finalizedById`, `revision`.
6. `QuoteEvent{ type: "FINALIZED" }`.

PDF генерувати через `renderQuotationHtml` + наявний `pdf.ts`. Нічого в геометрії сторінки не чіпати: правила полів і масштабу описані в пам'яті проєкту (`quotation-print-geometry`), `@page` у `pdf.ts` лишається єдиним джерелом полів.

UI — вкладка «Revisions» на сторінці квоти: таблиця `label | дата | автор | сума | PDF`. Підписана ревізія позначена бейджем. Diff між ревізіями у цей етап **не** входить.

## 6. Підписи

1. Прибрати з умов переходу в `SENT` будь-яку перевірку `managerSignedAt`. Форма на підпис іде клієнту з порожнім блоком менеджера.
2. `managerSignedAt` стає обов'язковим лише на переході `CLIENT_SIGNED → ACCEPTED`.
3. Блок підпису менеджера в PDF рендериться завжди; якщо підпису ще немає — порожнє поле під підпис (не «pending», просто лінія).
4. Підписна лінка для клієнта — токен на конкретну ревізію. Після `voidSignature` або після створення нової ревізії старий токен має віддавати 410 з текстом «Ця версія квоти більше не актуальна, зверніться до менеджера».

### voidSignature (адмін)

`POST /api/quotes/[id]/void-signature`, тільки admin, `reason` обов'язковий.

- Очистити `clientSignedAt`, `clientSignedName`, `clientSignedEmail`, `clientSignedIp`.
- `status = DRAFT`, `hasUnsentChanges = true`.
- `signedRevisionId` **не** чистити і снапшот підписаної ревізії ніколи не видаляти. Це юридичний слід: те, що клієнт підписав, лишається в базі назавжди, навіть якщо підпис анульовано.
- `QuoteEvent{ type: "SIGNATURE_VOIDED", reason }`.
- У вкладці Revisions підписана ревізія лишається з бейджем «Signed, voided {date} by {admin}».

## 7. Діалог надсилання клієнту

Це не «кнопка mailto». Клієнт має отримати акуратно зверстаний лист, який виглядає як документ від компанії, а не як системне сповіщення.

### 7.1 Тригер і попап

Кнопка `Send to client` активна при `FINALIZED` (і при `SENT`, якщо потрібне повторне надсилання). Відкриває модалку:

- **To** — передзаповнено email контакту клієнта, редаговане, можна додати кілька адрес.
- **Cc / Bcc** — згорнуті, розкриваються по кліку. Cc за замовчуванням містить email менеджера.
- **Subject** — передзаповнений шаблон.
- **Message** — textarea з передзаповненим текстом, підставлені змінні вже розкриті (менеджер бачить готовий текст, а не `{{client.firstName}}`).
- **Attachment** — нередагований чіп: `PQ-2026-0123-R1.pdf` з розміром файлу. Прикріплюється PDF **саме цієї ревізії зі снапшоту**, не регенерований з поточного стану.
- **Кнопки**: `Preview` (показує фінальний HTML листа в iframe, як його побачить клієнт) і `Send`.
- Модалка широка (≈720px), textarea на 10+ рядків, без скролу всередині скролу. Стан зберігається, якщо менеджер випадково закрив попап і відкрив знову (draft у локальному стані сторінки).

### 7.2 Змінні

Використати **наявний у репозиторії резолвер токенів** (той, що вже працює в блоках квоти), не писати новий. Знайти його і перевикористати. Мінімальний набір:

```
{{client.firstName}} {{client.lastName}} {{client.company}}
{{quote.number}} {{quote.label}} {{quote.revision}} {{quote.total}} {{quote.currency}} {{quote.validUntil}}
{{manager.firstName}} {{manager.fullName}} {{manager.title}} {{manager.phone}} {{manager.email}}
{{company.name}} {{company.website}} {{company.address}}
{{links.signQuote}}
```

`{{links.signQuote}}` — токенізована лінка на підписну сторінку конкретної ревізії. У листі це єдиний CTA: клієнт відкриває сторінку, читає, за потреби качає PDF і підписує там само. Окремого посилання «просто подивитися» не робимо, щоб не плодити двох різних URL на один документ.

Якщо токен не резолвиться — не лишати `{{...}}` у листі: підставляти порожній рядок і прибирати зайві пробіли/розділові знаки.

### 7.3 Дефолтні шаблони

Два варіанти, вибираються автоматично:

**Перше надсилання (`revision == 0`)**

```
Subject: {{company.name}} — Quotation {{quote.label}} for {{client.company}}

Hi {{client.firstName}},

Thank you for your interest in our cutting solutions. Please find attached
quotation {{quote.label}}, prepared for {{client.company}}.

The quotation is valid until {{quote.validUntil}}. If anything needs adjusting —
a different configuration, additional options, or delivery terms — just reply to
this email and I'll update it for you.

Kind regards,
```

**Повторне надсилання (`revision > 0`)**

```
Subject: {{company.name}} — Quotation {{quote.label}} (revised)

Hi {{client.firstName}},

As discussed, I've updated the quotation. Attached is revision {{quote.label}},
which replaces the previous version.

Let me know if this works for you or if you'd like any further changes.

Kind regards,
```

Шаблони зберігати в налаштуваннях (редаговані адміном), у коді лишити константи-фолбек.

### 7.4 HTML-лист

Верстка під поштові клієнти, не під браузер:

- Табличний layout, ширина 600px, всі стилі inline, без flex/grid, без зовнішнього CSS.
- Темна тема пошти не повинна ламати лист: фони задавати явно.
- Структура: логотип у шапці → привітання і текст менеджера (переноси рядків зберігаються) → картка-підсумок (номер і ревізія, конфігурація одним рядком, сума, дійсно до) → кнопка `Review & sign quotation` → `{{links.signQuote}}` (bulletproof button на `<table>`, не `<a>` зі стилем padding) → підпис менеджера → футер компанії.
- Підпис у футері підставляється автоматично: `{{manager.fullName}}`, посада, телефон, email, сайт, адреса компанії. Менеджер його не набирає і не може зіпсувати.
- Обов'язково plain-text альтернатива (`text/plain` частина) — без неї лист ловить спам-фільтри.
- PDF прикріплюється як attachment, а не лінкою.
- Alt-тексти на картинках, `role="presentation"` на layout-таблицях.

Перевірити рендер у Gmail, Outlook (desktop) і на iOS Mail.

### 7.5 Серверна частина

`POST /api/quotes/[id]/send`:
1. Права: owner або admin. Статус має бути `FINALIZED` або `SENT`.
2. Взяти останню `QuoteRevision`, прикріпити її `pdfPath`.
3. Відправити через наявний поштовий транспорт репозиторію (знайти конфіг, нову залежність не додавати).
4. `status = SENT`, `sentAt = now()`, `hasUnsentChanges = false`.
5. Записати `QuoteEmail` з фінальним текстом і `QuoteEvent{ type: "SENT" }`.
6. Помилка відправки не повинна лишати квоту в `SENT`: статус міняти тільки після успішної відповіді провайдера.

Історія листів — окремим блоком на сторінці квоти: кому, коли, яка ревізія, з можливістю розгорнути текст.

## 8. Підписна сторінка клієнта

### 8.1 Проблема з мобільним

Сам аркуш на телефоні поводиться добре: масштабується, читається. Але кнопка підпису в футері живе всередині того ж контейнера, що й аркуш, тому зменшується разом із ним. При зменшеному масштабі в неї неможливо влучити пальцем.

Причина, яку треба врахувати при виправленні: `position: fixed` всередині елемента з `transform` позиціонується відносно цього елемента, а не вікна. Тобто просто дописати `position: fixed` кнопці, залишивши її нащадком wrapper'а з `transform: scale()`, не спрацює.

### 8.2 Виправлення

Панель дій має бути **сусідом** контейнера аркуша, а не його нащадком:

```
<div class="pq-signing-page">
  <div class="pq-sheet-viewport">   ← тут зум, transform: scale()
     <div class="pq-sheet"> ... </div>
  </div>
  <div class="pq-action-bar"> ... </div>   ← поза зумом, position: fixed
</div>
```

Зум робимо свій, на `.pq-sheet-viewport` (жест pinch → `transform: scale`, плюс кнопки `+` / `−` / `Fit width`), а нативний pinch-zoom сторінки вимикаємо. Якщо лишити нативний, `position: fixed` теж візуально масштабується разом із visual viewport, і доведеться контр-скейлити панель через `window.visualViewport` на кожен `resize`/`scroll` — це працює, але гірше контролюється. Свій зум надійніший, бо панель тоді просто ніколи не масштабується.

Параметри панелі:
- `position: fixed; bottom: 0; left: 0; right: 0`, `padding-bottom: env(safe-area-inset-bottom)`.
- Висота 72-88px, фон непрозорий, тінь зверху, щоб відділялась від аркуша.
- Головна кнопка `Sign quotation` на всю ширину мінус паддінги, висота не менше 48px, шрифт не менше 16px.
- Вторинна дія `Download PDF` поруч або рядком вище, теж не менше 44px по висоті.
- Короткий незменшуваний текст над кнопкою, одним рядком, напр. `Quotation PQ-2026-0123-R1 · Valid until 30 Oct 2026`. Повний юридичний текст згоди не в панелі, а в модалці підпису.
- Нижній відступ у `.pq-sheet-viewport` на висоту панелі, щоб останній рядок аркуша не ховався під нею.

### 8.3 Флоу підпису

1. Тап на `Sign quotation` → bottom sheet модалка: поле `Full name`, `Email` (передзаповнений з контакту клієнта), чекбокс згоди з повним текстом, кнопка `Confirm signature`.
2. Сервер: `clientSignedAt/Name/Email/Ip`, `status = CLIENT_SIGNED`, `signedRevisionId`, `QuoteEvent{ type: "CLIENT_SIGNED" }`.
3. Генерується підписаний PDF: та сама ревізія, але з заповненим блоком підпису клієнта (ім'я, дата, IP). Зберігати окремим полем `signedPdfPath` на `QuoteRevision`, оригінал не перезаписувати.
4. Екран успіху замість аркуша: підтвердження, кнопка `Download signed PDF`, рядок «A copy has been sent to {email}».
5. Листи після підпису:
   - клієнту — підтвердження з підписаним PDF у вкладенні;
   - менеджеру (owner) — сповіщення «{client.company} signed {quote.label}» із сумою, датою, лінкою на квоту і підписаним PDF. Cc адміну продажів, якщо така роль є в системі.
6. Повторний захід за тією ж лінкою після підпису показує екран успіху з кнопкою завантаження, а не форму підпису.

### 8.4 Завантаження PDF

Кнопка `Download PDF` доступна **до** підпису теж: клієнт має мати змогу роздрукувати і роздивитися на папері перед рішенням. Віддавати PDF тієї ж ревізії, з іменем файлу `PQ-2026-0123-R1.pdf`. Після підпису кнопка віддає підписану версію.

## 9. Критерії приймання

- [ ] Менеджер фіналізує свою квоту, бачить `Unfinalize`, повертає в DRAFT, додає опцію, фіналізує знову → номер став `-R1`, у Revisions дві ревізії з різними PDF.
- [ ] Unfinalize → finalize без жодної зміни → номер лишився попереднім, нова ревізія не створена.
- [ ] Менеджер не бачить `Unfinalize` на чужій квоті; прямий POST повертає 403.
- [ ] Після підпису клієнта `Unfinalize` відсутній у всіх ролей; адмін має `Void signature` з обов'язковою причиною.
- [ ] Після `voidSignature` снапшот підписаної ревізії лишився в базі і відкривається.
- [ ] Квота надсилається клієнту без підпису менеджера.
- [ ] Перехід в `ACCEPTED` без підпису менеджера заблокований.
- [ ] Попап Send передзаповнений, змінні розкриті, PDF прикріплений з правильним label ревізії.
- [ ] Стара підписна лінка після нової ревізії віддає 410.
- [ ] Банер про ненадіслані зміни з'являється після unfinalize надісланої квоти і зникає після повторного надсилання.
- [ ] На телефоні при будь-якому масштабі аркуша панель підпису лишається того самого розміру і кнопка натискається з першого разу.
- [ ] Останній рядок аркуша не перекривається панеллю, на iPhone панель не заходить під home indicator.
- [ ] `Download PDF` працює до підпису; після підпису віддає підписану версію.
- [ ] Після підпису менеджер отримує лист зі сповіщенням і підписаним PDF, клієнт — своє підтвердження.
- [ ] Повторний перехід за підписною лінкою після підпису показує екран успіху, а не форму.

## 10. Порядок робіт

1. Схема + міграція + бекфіл ревізій для наявних фіналізованих квот.
2. Сервісний шар: `finalizeQuote`, `unfinalizeQuote`, `voidSignature`, `createRevisionSnapshot` з unit-тестами на переходи і на хеш.
3. Роути + перевірки прав.
4. UI: кнопки, діалоги, банер, вкладка Revisions.
5. Розділення підписів у формі й PDF.
6. Діалог Send + HTML-шаблон листа + історія листів.
7. Підписна сторінка: винесення панелі дій із зум-контейнера, свій зум, модалка підпису.
8. Підписаний PDF + листи після підпису (клієнту і менеджеру).

## 11. Нотатки щодо верифікації в пісочниці

- `npx prisma generate` у sandbox падає з `EPERM`. Після зміни `schema.prisma` `npx tsc --noEmit` сипле помилками на кожну нову колонку — це очікувано, не треба їх «лагодити». Забейслайнити їх і перевіряти, що не з'явився інший клас помилок. Міграції і `prisma generate` запускає Вадим локально.
- Робоча верифікація в пісочниці: `npx vitest run` і `npx eslint`.
- `npx tsc --noEmit` тут іде 90-150 секунд: довгий таймаут, вивід у файл, не пайпити через grep у тому ж виклику.
- Тести не повинні читати `RAW/` на імпорті (діюче правило репозиторію).
